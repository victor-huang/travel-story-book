# T17 — profile command (2026-07-26)

Built the Phase 0 profiler: `story-book profile <folder>`. 122 new tests, 308 total.

Two entries. One was a silent data-loss bug from a performance flag; one was a design question
about duplication that's worth recording because the reasoning generalizes.

---

### `exiftool -fast2` silently zeroed every video duration

**Cycle:** T17
**Cost:** ~5 min, caught by eyeballing output rather than by a test
**Category:** wrong-assumption

**Symptom.** The profile reported `videos 2 … 0s` for two fixtures known to be 3 seconds each.
No error, no warning — just a zero.

**Root cause.** I'd added `-fast2` as a throughput optimization for large libraries. For video,
`-fast2` stops before reading the `moov` atom, which is exactly where `Duration` lives. So the
field wasn't wrong, it was *absent*, and absent silently became `None` and then `0.0` in the
aggregate. Verified directly: `exiftool -json -n -fast2 -Duration clip.mov` returns only
`SourceFile`, while the same command without `-fast2` returns `"Duration": 3`.

**Fix.** Dropped `-fast2` entirely, with a comment at the call site saying why so nobody
re-adds it for speed. There is no runtime target for this project, which makes the tradeoff
one-sided — correctness wins by default. Added a backend regression test asserting the fixture's
duration reads as ~3s, named for the flag that broke it.

**Lesson.** **A speed flag that changes how much of a file gets read is a correctness flag.**
Before adding one, ask which fields it stops reading. And note the shape of this failure: an
optimization producing *plausible* output (0 seconds is a number, not a crash) is far more
dangerous than one that errors. This is exactly the class of bug that would have quietly
corrupted `video.transcribe = auto` decisions downstream, since T15 gates transcription on
duration.

### Whether the profiler should reuse T11's metadata extraction

**Cycle:** T17
**Cost:** ~0, a design call made deliberately
**Category:** design-note

**Symptom.** T17 needs EXIF (dates, GPS, device, duration). T11 owns metadata extraction. Naive
options were both bad: duplicate the EXIF read, or make the diagnostic depend on an unbuilt
stage plus a populated database.

**Root cause.** Not a bug — a genuine tension between DRY and the profiler's purpose. The
profiler exists to be run *before* anything works, on a folder that has never been imported, to
decide how the pipeline should be configured. A diagnostic you must build a database to run is a
diagnostic nobody runs.

**Fix.** The profiler does its own deliberately shallow read (one batched `exiftool -json` call,
~30 lines) and touches no DB. The module docstring states that T11 owns the real extraction —
persistence, timezone resolution, per-device clock offsets — so the overlap is bounded and
intentional rather than accidental.

What was *not* duplicated: the media-extension allowlist. That went into a new shared
`story_book/media_types.py`, because two different answers to "is this file media?" would be a
real bug — the profiler would report counts the scanner won't import. The tracker now flags that
T10 must import from it rather than fork it.

**Lesson.** Duplication of *logic* is sometimes the right call for a standalone diagnostic;
duplication of a *definition* two components must agree on is not. Split on that line: shallow
readers can be redundant, shared vocabulary cannot. When you do accept duplication, say so in
the docstring and name who owns the canonical version — otherwise the next person consolidates
them and reintroduces the coupling you were avoiding.

## Encoded as project rules

- `-fast2` is documented as forbidden at the exiftool call site, with the reason.
- The extension allowlist lives in one module; the tracker instructs T10 to import it.
- `CLAUDE.md` already carried "batch ExifTool into one process for the whole run"; the profiler
  implements it via `-@ -` over stdin, which also keeps an 8,000-file folder under `ARG_MAX`.
