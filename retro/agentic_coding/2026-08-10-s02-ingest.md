# S02 — ingest, presigned uploads, and what a fake does not prove

**Cycle:** Wave S / S02 (service ingest)
**Suite:** `service/` 19 → 119 tests; root suite 1772, unchanged.

---

### The test I did not write, because `moto` would have passed it for the wrong reason

**Cost:** ~15 min of probing, and it prevented a false claim rather than fixing a bug.
**Category:** wrong-assumption / near-miss

**Symptom.** The plan was to bind the upload's size into the presigned URL (`ContentLength` in the
signed parameters) and prove it with a test: PUT the wrong number of bytes, expect a 4xx. Before
writing it I probed what `moto server` actually enforces:

```
correct length -> 200
wrong length   -> 200
expired (by 1s)-> 200
tampered sig   -> 200
unsigned PUT   -> 200
```

**Root cause.** A fake implements an API's *shape*, and enforcement is not shape. I had been about to
treat "the test passes against moto" as evidence about S3. Worse, the test would have had to be
written *inverted* to pass — asserting the upload succeeds — and then it would have silently become a
test that the binding does **not** work.

**Fix.** The signed `Content-Length` stayed (it is right, and real S3 enforces it), but the suite
asserts only what can be observed locally: that `X-Amz-SignedHeaders` contains `content-length`, that
`X-Amz-Expires` matches the configured TTL, and that a genuine HTTP `PUT` to the URL round-trips and
is then found by `head`. The docstrings say, at each site, that enforcement is a property of S3 and is
not measured here. `moto[server]` rather than `mock_aws` for the same reason: a presigned URL is only
proven by a request made from outside botocore, which is what the phone does.

**Lesson.** **A fake tells you the shape of an API, never its enforcement.** Before writing a test
whose subject is a rejection, check that the double can reject. This is the same family as
`ffmpeg -v error` silencing the `volumedetect` output being parsed: the measurement instrument was the
bug, and the assertion happened to have the polarity that hid it.

### `have` was going to be a stronger claim than the service can make

**Cost:** ~10 min of thinking, no rework.
**Category:** design-flaw (caught before shipping)

**Symptom.** The natural reading of hash negotiation is "the service already has this photograph". It
does not: the whole point of a presigned `PUT` is that the bytes never pass through the API server,
so nothing on the server side ever hashes them. `have` can only mean *an object of the declared length
sits at that key*.

**Root cause.** Hash-addressed storage feels self-verifying because in the pipeline it is — `scan`
computes the hash from the bytes it is looking at. Move the write off-server and the address becomes a
claim by the client.

**Fix.** Three things, all of them statements of the limit rather than attempts to remove it. The
response carries `upload.presence_not_verified`. A stored length that disagrees with the declaration
is treated as **missing**, so the asset re-uploads rather than being trusted, and the entry says
`replaces_mismatched_object: true` — the one contradiction a service that never reads bytes can
detect. And the default object-key layout became **per user**, because under a global
content-addressed layout an account could `PUT` chosen bytes at another account's asset key and that
account's next negotiate would answer `have`. That last point is now the decisive argument recorded
against open question 4.

**Lesson.** **When a design removes a read, ask which claims depended on it.** "Never proxy the media"
is correct and it costs verifiability; the artifact has to say so at the point a consumer would assume
otherwise. Same rule as `video_proxies_included` and `privacy.home_configured`.

### `story-book init` cannot run when a trip is created

**Cost:** ~10 min, one throwaway CLI run.
**Category:** wrong-assumption

**Symptom.** S02's acceptance criterion says the scaffolding uses `story-book init --trip-dir`, and
the obvious place for it is `POST /trips`. Run against an empty directory, `init` **succeeds**:

```
Warnings
  • no importable media found in this folder.
wrote .../config.toml
```

**Root cause.** `init` *profiles* the folder and writes what it measured. With no media it measures
nothing, so every threshold silently stays at its shipped default — and `write_trip_dir` then
*refuses to overwrite an existing config*, so that non-measurement is permanent for the life of the
trip. Exit code 0 the whole way.

**Fix.** Scaffolding moved to `source:prepare`, after the uploads have been materialised onto the
filesystem, and it refuses while any declared asset is still missing — a config measured from a trip
that is two photographs short is never re-measured either. The response says `scaffolded: false` with
the reason rather than pretending.

**Lesson.** **A command that succeeds on empty input is a command that can be called too early.** The
project's existing rule is "if a fixture needs a setup line, ask who runs it in production"; the mirror
of it is *ask what this command measures, and whether the thing it measures exists yet.*

### The rename reached the batch, not the trip

**Cost:** ~10 min. One red test, and the test was right.
**Category:** design-flaw caught by a test

**Symptom.** `test_a_collision_arriving_in_a_later_batch_renames_the_earlier_asset_too` failed:
`{'IMG_0001.JPG', 'IMG_0001~f9393d09.JPG'}` where both should have carried a suffix.

**Root cause.** Two cameras both produce `IMG_0001.JPG`, and materialising each asset to
`<source>/<filename>` overwrites one with no error at all — so colliding names have to be
disambiguated. I computed the names over the trip's whole asset set (correct) and then wrote database
rows only for the batch being negotiated (wrong), so an asset declared in an earlier request kept its
plain name. That makes the stored filename a function of arrival order, and the stored filename is
exactly what `overrides.toml` addresses by — two identical trips uploaded in different orders would
produce corrections that do not carry across.

**Fix.** Negotiate rewrites the rows for the whole set. That has a consequence the first version did
not: an asset already fetched to disk under the old name is now stale, so `materialise_source`
reconciles the folder against the declared set, deletes what is no longer claimed, and reports it in
`removed`. Left alone, the scanner would have read the old file as a second photograph of the same
moment.

**Lesson.** **"Nothing derived from insertion order leaves the database" applies to derived names, not
just ids** — and when a derived value is stored, changing the derivation means reconciling everything
already stored under the old one. The second half is what nearly got missed: the correct fix to the
first bug created the second.

### A gap that lives only in a docstring is a gap that ships

**Category:** near-miss

There is no authentication in this service. That is S06's job, and S02 needed *some* notion of a user
to scope by, so `principal.py` reads an `X-Story-Identity` header and believes it. Writing that in a
docstring felt sufficient and is not: the session that opens a hole and the deployment that closes it
are months apart.

**Fix.** The service logs a warning at every start — "authentication is not implemented … any caller
may act as any user" — and a test asserts the warning is emitted. Separately, every index read is
scoped by `owner_id` **in SQL**: `Index.get_trip` cannot be asked without one, so a route physically
cannot forget. The isolation tests were shown to fail by dropping `owner_id` from the two `WHERE`
clauses (5 failures), and the acceptance criterion was shown to fail by making `head` always return
`None` (3 failures, including the criterion itself).

**Lesson.** Prefer an interface that cannot express the mistake over a comment asking callers not to
make it — and where a temporary hole is genuinely necessary, make the *running system* say so, not the
source.
