# S03 — the job queue, and progress that had to be read rather than reported

**Cycle:** Wave S / S03. 61 new service tests (119 → 180); root suite unchanged at 1772.

---

### Five of eighteen stages reported "complete" one second into a build

**Cost:** ~15 min to find, ~10 to fix. Found by printing the real response body, not by a test.
**Category:** design-flaw / wrong-assumption

**Symptom.** `GET /jobs/{id}` on a job that had been running for under a second:
`stages_complete: 5`, `media_known: 0`, and five per-item stages each reading
`state: "complete", total: 0, detail: "no candidate items: this stage does not apply to this
library"`. A client drawing a bar from `stages_complete / stages_total` would have shown a quarter
done over a build that had not yet read a photograph.

**Root cause.** The denominator for a per-item stage is `len(stage.select(ctx))`, and before `scan`
commits, the `media` table is empty — so *every* per-item stage selects nothing. Zero candidates and
zero completed satisfies `done >= total`, which the code read as "finished". The false belief:
**an empty candidate set means the stage has nothing to do.** It can equally mean nothing has been
discovered yet, and the two are opposite claims.

**Fix.** `total == 0` is only "does not apply" when `count_media(conn) > 0`; otherwise the stage is
`pending` with `total: null` and a detail saying the library has not been scanned. Two tests, plus
the control that a genuinely inapplicable stage (`video` over an all-stills library) still reads
complete once the scan has run — without that control the fix could have been "never report
complete", which is a different lie.

**Lesson, and it is the house rule rather than a new one.** *Look at real output.* Fifteen tests
were green over a body that said something untrue on its first second of every build, because every
one of them asserted on a *finished* build. A test that only ever samples the steady state cannot
see a wrong transient, and progress is entirely transient.

### The denominator that walks down to meet the numerator

**Cost:** ~0 — caught while reading `EmbeddingStage` before writing the reader.
**Category:** near-miss / wrong-assumption

`PerItemStage.select` is documented as "all items this stage would like to process, **before cache
filtering**" — and `EmbeddingStage.select` does its own cache filtering anyway, against the
`embedding` table, because its `stage_result` key carries no model tag and changing `clip_name` must
re-embed everything. So `len(select())` *shrinks* as the stage progresses. Taken as a total it would
have produced a stage that reported 100% while half its work was outstanding: a bar that fills
because the goalpost moved.

The published total is `select() ∪ already-completed ∪ failed`, which is monotone for a
self-filtering stage and identical to `select()` for every other one. The test that guards it needed
its own control: the first version subclassed a stage under a *new* name, so its own completed set
was empty, both totals came out equal for a trivial reason, and the test proved nothing. Naming it
`metadata` — a stage whose rows really are complete in the fixture database — made the naive
denominator measurably `0` and the published one `25`. **The docstring described the contract; two
of the eighteen stages do not honour it, and a reader of the base class alone would not know.**

### `zip(xs, xs[1:], strict=True)`, one line after reading the warning against it

**Cost:** ~2 min, one red test.
**Category:** wrong-test

`CLAUDE.md` lists this exact idiom as a bug that already cost this project a session. I wrote it in
the monotonicity test anyway and got `ValueError: zip() argument 2 is shorter than argument 1`.
`itertools.pairwise` is the same intent with no off-by-one available. Worth recording only because
the lesson was *already written down and freshly read* — a warning in prose does not survive contact
with a hurried line, and the enforceable version is to reach for `pairwise` by habit.

### A monotonicity assertion that a constant would have satisfied

**Cost:** ~5 min of thought, no failure.
**Category:** near-miss

"Counts advance monotonically" is satisfied by an endpoint that returns the same numbers for ever,
which is precisely the failure mode this task is most likely to ship. The test therefore also asserts
that the samples contain **more than one distinct reading**, and that the finished job's position is
strictly greater than the first running sample's. *Pair every measurement with a control that must
differ from it* — a bad progress endpoint fails the control, not the ordering.

The same shape applies to the resume half of the acceptance criterion: "the second build reused the
cache" is asserted as *every per-item `computed_at` is unchanged*, with `scan`'s — `always_run`, so
it must recompute — required to be **newer**. Without the second half, a build that never ran would
pass. `computed_at` has one-second resolution, so the test sleeps 1.1 s between builds; at higher
resolution neither half would have been falsifiable.

### `--no-cloud` is a flag, not a config field, and availability measured from the config lied

**Cost:** ~10 min, one confusing test failure.
**Category:** wrong-assumption

Job records carry which stages this deployment could run, measured by calling each stage's own
`available(ctx)`. Built from `Config.load(config_path)` alone, that reported `landmarks` as
**available** — while every build the worker runs passes `--no-cloud`, which the CLI applies over the
config, and which makes `landmarks` skip. So a finished, successful job reported `landmarks` as the
current stage with `0/22` outstanding for ever. The context a measurement is taken in has to be the
context the work ran in: `measure_capability` now takes the flag the build will actually receive.

### What was deliberately left undecided, and said so

- **Question 16 (the queue) is proposed, not settled.** A `job` table claimed in one
  `BEGIN IMMEDIATE`, no broker, worker in the same image. It is written down in the tracker with
  what it costs: **it expires the moment a second instance exists**, and nothing in the code would
  detect a second worker on another machine, because the trip directory is local.
- **`POST /trips/{id}/build` accepts no `{config, overrides}`**, which `ios_backend_service.md`'s
  endpoint list shows. `story-book init` *measures* the config from the uploaded media and then
  refuses to overwrite it, so a client-supplied config would make a cached guess permanent. Config
  ownership is open question 8; the deviation is recorded rather than quietly implemented.
- **No percentage is published.** Not an omission — a test asserts no field named `percent`,
  `fraction` or `eta` exists, so adding one fails rather than passing review.
